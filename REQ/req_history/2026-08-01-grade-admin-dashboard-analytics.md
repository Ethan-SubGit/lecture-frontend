# 2026-08-01 — 대시보드 확장 분석 8종 (grade-admin)

## 요청 원문

> api내용이 추가되었어. 대시보드에 내용을 추가하고싶어. 화면 업데이트 해줘

반영 범위를 되물었을 때 사용자가 선택한 답:

> 전부 기존 /dashboard에 섹션 추가

## 해석한 의도

- 백엔드 Swagger를 재조회해 `REQ/openapi.json`을 최신화한 결과, 기존 `GET /dashboard/summary` 외에 **대시보드 분석 엔드포인트 8개가 신설**되어 있었다.
  1. `GET /dashboard/at-risk-students` — 학사경고 위험군 (F학점 수 **또는** 평균 성취도, OR 결합)
  2. `GET /dashboard/component-analysis` — 평가항목별(중간고사/중간과제/기말고사/기말과제), 시험 vs 과제 격차, 전반부 대비 후반부 향상도. `overall` + `byLecture`
  3. `GET /dashboard/department-achievement` — 학과별 평균/중앙값/표준편차/최소·최대/평균GPA/A·F비율 + 학과 × 등급 교차표
  4. `GET /dashboard/department-lecture-matrix` — 강의(행) × 학과(열) 교차표, 강의 평균 대비 학과별 편차
  5. `GET /dashboard/lecture-difficulty` — 강의별 난이도 + 학점 인플레이션(A비율 ≥ 50%) / 난이도 이상치(EASY·HARD) 플래그
  6. `GET /dashboard/score-histogram` — 합계점수 구간별 인원수·비율
  7. `GET /dashboard/student-ranking` — 학번 단위 종합 평균 GPA 랭킹 (SQL `RANK()`, 동점 처리)
  8. `GET /dashboard/term-trend` — 학기별 시계열, `breakdown=department`로 학과별 시리즈 추가 가능
- 사용자는 이 8종을 **새 화면이 아니라 기존 `/dashboard` 안의 추가 섹션**으로 보고 싶어 한다. 즉 라우트·사이드바 메뉴는 건드리지 않는다.
- 요청 문장이 "내용을 추가"이지 "조건을 바꿔가며 분석"이 아니라는 점이, 필터 UI 범위 결정의 출발점이 되었다.

## 확인한 질문과 답변

| 질문 | 답변 | 출처 |
|---|---|---|
| 8개 API를 어디에 반영할까 (새 메뉴/새 화면/기존 대시보드 확장) | **전부 기존 `/dashboard`에 섹션 추가** | 사용자 선택 |

그 외에는 사용자에게 되묻지 않고, 아래 「확정된 결정 사항」대로 판단해 진행했다. 되묻지 않은 이유: 관례적 기본값이 있거나(로딩·에러 처리 단위), 결정을 나중에 뒤집어도 응답 스키마·섹션 구조가 바뀌지 않아(필터 범위) 되돌리기 비용이 낮기 때문이다. 뒤집힐 가능성이 있는 판단은 전부 spec.md 「9. 미결 사항」에 올려 두었다.

## 확정된 결정 사항

### 1. 반영 위치 — 새 라우트·새 메뉴 없음

기존 `/dashboard` 한 페이지에 8개 섹션을 이어 붙인다. 「4.2 사이드바 메뉴 항목」 표는 변경 없음. 라우트 표의 `/dashboard` 행 역할 설명만 갱신했다.

### 2. 필터 UI 범위 — **이번 라운드는 무필터(전체 집계)** (spec.md 「2.1」)

8개 엔드포인트를 `term`·`departmentId`·`lectureId` 없이 호출한다. 근거 5가지:

1. 요청이 "내용 추가"였고 조건 탐색 요구가 없었다.
2. 기존 `/dashboard`에 필터 UI가 전혀 없다. 필터 도입은 화면 성격을 "요약판 → 분석 도구"로 바꾸는 별도 합의 사항이다.
3. 섹션별 개별 필터는 컨트롤 24개(8×3)를 만들고, 숫자마다 모집단이 달라져 해석이 불가능해진다.
4. 공통 필터 바 하나도 이르다 — 필터 변경 시 8요청 동시 재발화 + 섹션별 부분 실패 처리가 곱해지고, 결정적으로 **필터 선택지의 데이터 소스가 없다**(학기 목록 API 부재, 학과·강의 드롭다운을 위해 `GET /departments` + `GET /lectures` 추가 호출 필요).
5. 되돌리기 비용이 낮다 — 필터는 전부 선택 파라미터이고 미전송 시 전체 집계가 온다. 나중에 얹어도 응답 스키마·섹션 구조가 그대로다.

단, **호출 함수는 처음부터 공통 필터 객체를 선택 인자로 받는 시그니처**로 정의하게 했다(`DashboardFilterQuery`). 다음 라운드에서 시그니처를 고치지 않아도 되게 하기 위함이다.

### 3. 필터 외 파라미터는 상수로 고정 (spec.md 「5.5」)

| 엔드포인트 | 전송 | 근거 |
|---|---|---|
| `score-histogram` | 미전송 (`bucketSize=10`) | 10점 단위가 관습적 눈금. 응답의 `bucketSize`를 화면 문구에 그대로 써서 값이 바뀌어도 어긋나지 않게 함 |
| `lecture-difficulty` | 미전송 (`minStudentCount=1`) | 소규모 강의를 임의로 감추면 설명 불가능한 누락이 생긴다. 인원수 컬럼 노출로 대신함 |
| `term-trend` | 미전송 (`breakdown=none`) | 학과별 다중 시리즈는 범례·색 배정이 필요한 별도 시각 과제 |
| `student-ranking` | `limit=10` (기본값과 동일하나 명시) | 화면 문구 "상위 10명"이 서버 기본값 변경에 흔들리지 않게 |
| `at-risk-students` | `limit=20` | 서버 기본 50은 대시보드 한 섹션에 과하다. 응답에 총원 필드가 없어 "N명 중"을 쓸 수 없으므로 받은 건수 = 표시 건수로 맞춤 |
| `at-risk-students` | `averageBelow`/`failCountAtLeast` 미전송 (60/1) | 학사경고 통상 기준선. 화면 문구는 **요청값이 아니라 응답값**을 출력해 안내가 거짓말이 되지 않게 함 |

### 4. 로딩·에러 처리 단위 — **섹션 단위 독립** (spec.md 「6.1」)

- **결정 1** 섹션마다 로딩·빈·에러·재시도를 독립적으로 갖는다. `Promise.all`로 묶지 않는다 — 9개 중 1개 실패로 대시보드 전체가 에러 화면이 되는 구조를 만들 이유가 없고, 화면 완성 시간이 가장 느린 하나에 끌려간다.
- **결정 2** 마운트 시 9건(summary 1 + 확장 8)을 **병렬 발사**. 확장 8건은 summary를 기다리지 않는다.
- **결정 3** [다시 시도]는 섹션 로컬. 전역 "전체 다시 조회" 버튼은 두지 않는다(성공한 섹션까지 재호출됨).
- **결정 4** 401은 섹션이 처리하지 않고 기존 전역 단일 처리에 맡긴다(리다이렉트 1회 억제).
- **결정 5** 성적 0건(`totalStudentScores === 0`)이면 8섹션을 **렌더만 억제**한다. 호출은 막지 않는다 — summary 도착을 기다렸다 8개를 호출하면 첫 화면 완성 시간이 두 배가 된다.
- 기존 자산 `hooks/useAsyncData.ts`가 이미 조회 1건 단위이므로 **섹션 = 훅 1개**로 새 상태 관리 장치 없이 성립한다.

### 5. 데이터 해석 문구 — 숫자만 던지지 않는다 (spec.md 「3.7」)

- `gradeInflation === true` → **"학점 인플레이션 의심"** + 근거("A등급 비율 50% 이상"). "비정상" 같은 오류 어감 금지.
- `difficultyOutlier` → `"EASY"` = **"평균 대비 쉬움"**, `"HARD"` = **"평균 대비 어려움"**, `null`이면 배지 자체를 그리지 않는다. 근거("전체 평균과 10%p 이상 차이") 병기. 두 플래그가 동시에 참이면 라벨 2개.
- `riskReasons` → 서버가 준 한국어 문장을 **원소 전부 그대로** 표시(2개면 2개 다). 클라이언트가 재작성·선별하지 않는다.
- 위험군 판정 → **"F학점 N개 이상 또는 평균 성취도 M% 미만"** — OR임을 반드시 문구로 명시(AND로 오해하면 명단 크기를 잘못 읽는다).
- `examVsAssignmentGap`, `improvement`, `deviationFromOverall`, `deviationFromLectureAverage` → 부호와 함께 표시하고, 부호의 의미를 문장으로 풀어 준다.
- `stddevTotalScore` / `medianTotalScore`의 `null` → **`0`이 아니라 `—` + "계산 불가"**. OpenAPI가 "0이 아니다"라고 못 박고 있고, 0으로 표시하면 "편차 없는 균일한 학과"라는 정반대 의미가 된다.
- `rank` → 응답값 그대로. 동점 구간(`1,2,2,4`)을 클라이언트가 재계산하지 않는다.

### 6. 백분율 분모는 응답 `totalScoreMax`

클라이언트 상수 `MAX_SCORE`(100)를 쓰지 않는다. 서버 설정 `DASHBOARD_TOTAL_SCORE_MAX`가 100이 아닐 수 있다.

### 7. 섹션 배치 순서는 **구조 제안까지만** (spec.md 「4.4」)

전체 분포 → 학과 축 → 강의 축 → 두 축의 교차 → 점수 내부 구성 → 시간 축 → 개인 단위 순으로 11개 섹션 순서를 제안했다. **열 구성·카드 크기·차트 종류·색상은 전부 `ui-ux-designer` 소관**이며, 디자이너가 근거를 갖고 순서를 조정해도 수용 기준에 영향이 없도록 기준을 "순서"가 아니라 "존재와 내용"으로 작성했다.

### 8. 기존 통계 3블록은 유지 (삭제하지 않음)

`summary.departmentStats`/`lectureStats`/`termStats`는 각각 `department-achievement`/`lecture-difficulty`/`term-trend`에 **정보가 완전히 포섭**된다. 그럼에도 이번 라운드에서 삭제하지 않았다 — 이미 노출 중인 것을 없애는 결정은 사용자 확인이 필요하다. 하단으로 순서만 내리고, 삭제 여부는 미결 사항으로 올렸다.

## 남긴 가정

spec.md 「9. 결정한 가정」 19~31번으로 기록했다. 요약:

- (19) 필터 UI 미구현 — **사용자 검토 1순위**
- (20) 섹션 11개가 세로로 이어지는 긴 한 페이지 구조 허용 (탭·아코디언 분할 안 함)
- (21) 9개 동시 요청. HTTP/1.1 동시 연결 한도로 일부 대기 가능하나 선제적 직렬화는 안 함
- (22) 집계 API 응답 시간 미측정. 결과 캐싱 없음(진입할 때마다 최신값)
- (23) `totalScoreMax`가 100이 아닐 수 있다고 보고 응답값을 분모로 사용
- (24) `null` 통계값을 0이 아닌 "계산 불가"로 표시
- (25) 서버 생성 한국어 문자열은 그대로 사용. 예외는 `EASY`/`HARD` 매핑뿐
- (26) 위험군 `limit=20`은 화면 분량 판단
- (27)(28) `minStudentCount`/`minLectureCount`를 1로 두어 소규모 표본도 표시하되, 인원수·강의 수 컬럼으로 왜곡을 사용자가 알아볼 수 있게 함
- (29) 랭킹·위험군의 집계 단위가 학번이라는 백엔드 한계를 화면 각주로 노출
- (30) 기존 통계 3블록 유지
- (31) 지연 로딩(lazy) 없이 진입 시 전부 호출

미결 사항(구현 전 확인 필요)에는 필터 UI 필요 여부, 기존 3블록 삭제 여부, `breakdown=department` 필요 여부, 위험군 표시 인원, `DASHBOARD_TOTAL_SCORE_MAX` 실제값, 9개 동시 호출의 실측 성능, **개인 식별 정보(학번·이름) 명단을 대시보드 첫 화면에 노출해도 되는지**, 교차표의 열 폭 한계를 올렸다.
